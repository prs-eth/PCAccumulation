# CLAUDE.md

Fork of the ECCV 2022 code "Dynamic 3D Scene Analysis by Point Cloud Accumulation"
(upstream: https://github.com/prs-eth/PCAccumulation), updated to run on modern GPUs.
University project (course *Structura Sistemelor de Calcul*): hardware-accelerate the network
(MotionNet) and deploy it on an **NVIDIA Jetson Orin Nano**.

Planning documents (Romanian): `docs/Roadmap.md` (weekly plan and deliverables). This file contains 
all the details of the plan in English; the plan remains the source of truth if they ever disagree.

## 1. Summary

- **Final requirement:** one C++/CUDA project built with one `CMakeLists.txt`, **no Python**. The
  same project builds on the laptop (x86, RTX 4060) and on the Jetson (ARM64, Orin Nano).
- **Data:** ~200 frames selected from `data.zip` (the paper's preprocessed dataset, ~300 GB, does not
  fit on the laptop or the Jetson). Real data, not generated data. Pretrained weights:
  `checkpoints/waymo.pth`. No training.
- Without Python, PyTorch, `torch_scatter`, numba and sklearn are gone. Everything the model does
  must exist in C++, in one of three forms:
  1. **TensorRT engines** for the neural-network parts: backbone, STPN, the MLPs and, with a fixed
     shape, even the Sinkhorn step of ego-motion. Trained weights reach them through ONNX files.
  2. **Custom CUDA kernels** for irregular ops: voxelisation, scatter/max over pillars, point
     selection, warp-grid generation and DBSCAN.
  3. **Plain C++ on the CPU** for control logic and small math: Kabsch / 3×3 SVD with Eigen and
     chaining 4×4 poses.
- **ONNX export stays a Python utility, separate from the C++ project.** The weights are in a `.pth`
  (PyTorch pickle) that C++ can't read, and ONNX export is needed for the Jetson anyway. The utility
  (to be created, e.g. `export_onnx.py`) is called from scripts whenever the models must be
  regenerated. The same utility converts the selected frames and the original model's outputs into
  binary reference files for the C++ tests. The C++ app only uses what the utility produces:
  `.onnx` and `.bin`.
- **Scope:** segmentation of moving objects, ending at the clustering module: every point gets a
  static/moving label and an object ID (plus the estimated ego-motion poses). TubeNet (`AlignNet`),
  which refines each object's motion for point cloud accumulation, is the hardest to port
  (per-object loops, variable shapes, many scatter ops) and is an **optional extension**.

## 2. Platform

| | Laptop | Jetson Orin Nano 8 GB |
|---|---|---|
| GPU | RTX 4060 Laptop, sm_89 | Ampere, 1024 CUDA cores, 32 Tensor Cores, sm_87 |
| Memory | separate CPU/GPU | 8 GB LPDDR5 **shared**, 68 GB/s (102 GB/s in super mode) |
| Software | CUDA 12.4 (system) + TensorRT 10.3 C++ (to install) | JetPack 6.2: CUDA 12.6, cuDNN 9.3, **TensorRT 10.3** |
| DLA | - | **none** (DLA only exists on Orin NX / AGX) |
| CMake | distribution version | 3.22 (Ubuntu 22.04) |

- **Acceleration is GPU-only**, through TensorRT and CUDA.
- **On the laptop, install TensorRT 10.3 as the C++ package** (NVIDIA tar archive with headers and
  libraries). The pip wheel has no headers. The same version on both machines avoids differences in
  ONNX parsing.
- **Engines are built on the machine that runs them.** The C++ program builds them automatically
  from `.onnx` on first run and saves them to disk. Never copy `.engine` files between machines.
- **CMake 3.22 doesn't support `CMAKE_CUDA_ARCHITECTURES=native`**: pass the arch explicitly,
  `-DCMAKE_CUDA_ARCHITECTURES=87` on the Jetson and `89` on the laptop.
- **Use super mode** (25 W / MAXN SUPER) and always report the power mode used for a measurement.

## 3. C++ project structure

```
pcacc_cpp/
├── CMakeLists.txt
├── include/            # headers (config, types, module interfaces)
├── src/
│   ├── main.cpp            # reads frames, runs the pipeline, writes the result
│   ├── pointcloud_io.cpp   # reads binary frames, writes results (.bin / .ply)
│   ├── trt_engine.cpp      # load / build engines, run them
│   ├── pipeline.cpp        # module order, GPU buffers, CUDA streams
│   ├── kabsch.cpp          # 3x3 SVD with Eigen
│   └── cuda/
│       ├── preprocess.cu   # crop + ground removal
│       ├── voxelize.cu     # points -> 4D pillars
│       ├── pillar_ops.cu   # per-point features, scatter-max, BEV scatter
│       ├── ego_motion.cu   # background pillar selection, sampling 1024 points
│       ├── warp.cu         # warp grids from estimated poses
│       └── dbscan.cu       # downsampling + DBSCAN on GPU
├── models/             # .onnx files (generated by the export utility)
├── data/               # selected frames + reference outputs (.bin)
└── tests/              # compare C++ modules with the reference
```

The export utility and the script that calls it live outside this project, next to the original
Python code, which they need to load the model.

Weekly deliverables in `docs/Roadmap.md` also name `test_modules.cpp`, `int8_calibrator.cpp`,
`streaming_cache.cpp`, `benchmark.cpp`, `benchmark_results.csv` and `README.md`.

`CMakeLists.txt` skeleton:

```cmake
cmake_minimum_required(VERSION 3.22)
project(pcacc LANGUAGES CXX CUDA)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CUDA_STANDARD 17)
if(NOT DEFINED CMAKE_CUDA_ARCHITECTURES)
  set(CMAKE_CUDA_ARCHITECTURES 87)          # Jetson; on the laptop: -DCMAKE_CUDA_ARCHITECTURES=89
endif()

find_package(CUDAToolkit REQUIRED)
find_package(Eigen3 REQUIRED)
set(TENSORRT_ROOT "" CACHE PATH "TensorRT path (empty on the Jetson, where it is in /usr)")
find_path(TRT_INCLUDE NvInfer.h HINTS ${TENSORRT_ROOT}/include /usr/include/aarch64-linux-gnu)
find_library(NVINFER nvinfer HINTS ${TENSORRT_ROOT}/lib)
find_library(NVONNXPARSER nvonnxparser HINTS ${TENSORRT_ROOT}/lib)

file(GLOB SRC src/*.cpp src/cuda/*.cu)
add_executable(pcacc ${SRC})
target_include_directories(pcacc PRIVATE include ${TRT_INCLUDE})
target_link_libraries(pcacc PRIVATE CUDA::cudart CUDA::cublas ${NVINFER} ${NVONNXPARSER} Eigen3::Eigen)
```

- Laptop: `cmake -B build -DCMAKE_CUDA_ARCHITECTURES=89 -DTENSORRT_ROOT=~/TensorRT-10.3`. nvcc 12.4
  doesn't accept the default gcc 15, so add `-DCMAKE_CUDA_HOST_COMPILER=g++-13`.
- Jetson: `cmake -B build`.

## 4. Module map: Python → C++

BEV grid 288 × 288 cells (`range [-36, 36]`, `voxel_size 0.25`), T = 5 sweeps, C = 32 channels.
Ego-motion uses `n_kpts = 1024` and `sinkhorn_iter = 3`, in `skip` mode (4 pairs "frame → anchor").

| # | Original module | Does | C++ implementation |
|---|---|---|---|
| 0 | `prep_input` (`libs/dataset.py`) | crop, ground removal | CUDA `preprocess.cu` (filter + compaction) |
| 1 | `voxel_generator.py` (numba) | points → 4D pillars | CUDA `voxelize.cu` (pillar key + sort / hash) |
| 2 | `PillarFeatureNet` | point MLP + max per pillar | 3 small TRT engines (MLP, dynamic N) + scatter-max kernels between them |
| 3 | `scatter_point_pillar` | pillars → BEV image | CUDA `pillar_ops.cu` |
| 4 | `UNet` + `semseg_head` + `ego_feats_head` | 2D backbone, fixed shape | **TRT engine `backbone`** |
| 5 | `EgoMotionHead` | background selection, sampling, Sinkhorn, Kabsch | CUDA (selection + sampling) + **TRT engine `ego_ot`** (fixed 4 × 1024) + Kabsch with Eigen on the CPU |
| 6 | `warp_feats` | grids from poses + `grid_sample` | CUDA `warp.cu` (grids) + GridSample inside the `stpn` engine |
| 7 | `STPN` | Conv3d + UNet + per-point head | **TRT engine `stpn`** (fixed map, dynamic K points) |
| 8 | `Cluster` | downsampling + DBSCAN | CUDA `dbscan.cu` |
| 9 | `AlignNet` / TubeNet | per-object motion | **optional** |

## 5. Concrete steps

### Phase 0 - Data, reference and export (Python utility, on the laptop)

1. **Frame selection.** Pick ~200 frames from `data.zip` and extract only those, without unzipping
   the whole archive (e.g. `unzip data.zip <file>`). The `.npz` files use pickle, so never read them
   directly from C++. Convert them once into simple `.bin` files (header with the shape +
   float32/int32 data).
2. **Per-module profiling.** Add `torch.cuda.Event` timers in `MotionNet.forward` around each step of
   the table above and run the original model on the selected frames. If possible, do the same on
   the Jetson. The result is the **V0 baseline** for the final speedup.
3. **Reference data.** For a subset of frames, save as simple `.bin` files:
   - the input: points (x, y, z) and frame index;
   - intermediate outputs: pillars, `bev`, `bev_feats`, `fb_seg`, estimated poses, `mos_est`,
     `offset_est` and `inst_labels_est`;
   - the **indices sampled by `torch.randperm`** in ego-motion. The C++ tests use them to compare
     exactly, removing the difference caused by randomness.
4. **ONNX export.** Write `nn.Module` wrappers with fixed-shape inputs (dynamic only where needed)
   and run `torch.onnx.export(..., opset_version=17)`:

| Engine | Inputs | Outputs | Contents |
|---|---|---|---|
| `pfn_a/b/c` | per-point features `[N, 9]` (dynamic N) | `[N, 64]` / `[N, 32]` | `fc_pos`, the ResNet blocks, `fc_c` |
| `backbone` | `bev [5, 32, 288, 288]` | `bev_feats`, `fb_seg`, `geo_feats` (L2-normalized) | UNet + 2 heads |
| `ego_ot` | `feats_s/t [4, 1024, 64]`, `coor_s/t [4, 1024, 3]`, distance threshold `[4]` | `weighted_t [4, 1024, 3]`, `weights [4, 1024]` | distances, affinity (with learned `alpha` and `beta`), Sinkhorn with slack (3 iterations), `perm @ coor_t` |
| `stpn` | `bev_feats [1, 5, 32, 288, 288]`, grids `[4, 288, 288, 2]`, points `[K, 3]` (dynamic K) | `mos [K, 2]`, `offset [K, 2]` | warp (GridSample) + 4 × Conv3d + max over time + UNet + `ungrid` (GridSample on a `[1, 1, K, 2]` grid) + MLP + heads |

5. **Export verification.** Compare each `.onnx` with PyTorch in `onnxruntime`. The difference must
   be on the order of 1e-5.

**Watch out for `ungrid`** (`models/pillar_encoder.py`). The original rearranges points into
`[n+1, H, W, 2]` blocks to reuse `grid_sample`. In the export wrapper, put them directly in a
`[1, 1, K, 2]` grid. The bilinear result is identical.

### Phase 1 - C++ skeleton and preprocessing (`preprocess.cu`, `voxelize.cu`)

1. **Reading data.** `pointcloud_io.cpp` reads the `.bin` files; `main.cpp` takes the path of the
   frames and of the models folder.
2. **Crop and ground removal.** A kernel computes a per-point mask: `|x|, |y| < 32`, `-2 < z < 6`,
   `z > ground_height`. Then compact the points with `cub::DeviceSelect::Flagged` or
   `thrust::copy_if`.
3. **Voxelisation.** For each point compute the pillar key `(t, y, x)` (0.25 m cells). Sort by key
   (`cub::DeviceRadixSort::SortPairs`); `unique` / run-length encode gives the pillar list. From it
   derive `coordinates`, `point_to_voxel_map` and `num_voxels`.

   Pillar order may differ from the numba version. The test compares the sets after sorting, not
   the order.

### Phase 2 - Pillar encoder and BEV (`pillar_ops.cu` + the `pfn_*` engines)

1. **Per-point features.** A kernel computes the per-pillar mean (scatter-add + divide), then the 9
   features (x, y, z, distance to the mean, offset to the pillar center, t), normalized as in the
   original.
2. **Engine chain.** Alternate engines and kernels:
   - engine `pfn_a`;
   - kernel: scatter-max per pillar + gather back to points + concat;
   - engine `pfn_b`;
   - the same kernel;
   - engine `pfn_c`;
   - final scatter-max kernel, giving per-pillar features `[M, 32]`.

   For float max use `atomicMax` on the integer representation of the values. After ReLU they are
   non-negative, so the bitwise comparison is correct. Still check the sign of the outputs before
   each max.
3. **BEV image.** A kernel writes each pillar into the `[5, 32, 288, 288]` image. The same kernel
   also produces the occupancy map and the point-mean map needed by ego-motion.

### Phase 3 - Backbone and ego-motion (`trt_engine.cpp`, `ego_motion.cu`, `kabsch.cpp`)

1. **`trt_engine.cpp`:**
   - if a `.engine` exists, deserialize it;
   - otherwise build it from `.onnx` with `nvonnxparser` and optimization profiles for the dynamic
     inputs, then save it;
   - to run: `setTensorAddress` on the GPU buffers + `enqueueV3(stream)`.
2. **Backbone.** Run the `backbone` engine on the BEV image, with outputs written directly into GPU
   buffers.
3. **Ego-motion:**
   - for each frame, a kernel selects the occupied background pillars (`fb_seg` argmax = 0);
   - sample 1024 pillars (random permutation with `curand` and a fixed seed; in tests, the
     reference indices), padding with the last element if there are fewer;
   - a single call of the `ego_ot` engine processes all 4 pairs;
   - on the CPU, with Eigen, weighted Kabsch: centroids, 3 × 3 covariance matrix, `JacobiSVD`,
     reflection correction. The result is a 4 × 4 pose per frame.

   The copy to the CPU is only 4 × 1024 × 4 values, so negligible.

### Phase 4 - Motion segmentation (`warp.cu` + the `stpn` engine)

1. **Warp grids.** A kernel computes, from the inverse of each pose, the `[4, 288, 288, 2]` grid,
   exactly like `get_transformed_grid`.
2. **Point selection.** A kernel transforms all points into the anchor frame with the estimated
   poses. Then compact the foreground points (`fb_est_per_point == 1`): these are the K points sent
   to `stpn`.
3. **The `stpn` engine** gives `mos` and `offset` for the K points. Write them back into the full
   vectors: non-foreground points get "static" and offset 0.

### Phase 5 - Clustering (`dbscan.cu`)

1. **Point preparation.** Select the moving points (`mos` argmax = 1) and add their offset on x and y.
2. **Downsampling.** At 0.05 m, via voxel key + sort + `unique`, keeping the inverse map. Then set
   z = 0.
3. **2D DBSCAN** (`eps = 0.4`, `min_samples = 5`):
   - build a grid with cells of size `eps`;
   - for each point count the neighbours in the surrounding 9 cells to find the core points;
   - link neighbouring core points with union-find on the GPU (`atomicCAS` in `find` / `union`);
   - attach border points to a neighbouring core point.
4. **Final labels.** Drop clusters with fewer than 15 points, renumber labels 1..K and propagate them
   back to all points through the inverse map.

GPU DBSCAN won't necessarily give the same numbering as sklearn. Compare it by **partition
agreement** (e.g. adjusted Rand index or IoU between matched clusters), not by equality.

### Phase 6 - Integration and verification (`pipeline.cpp`, `tests/`)

1. **Pipeline.** `pipeline.cpp` allocates all GPU buffers once, at startup, at the maximum sizes seen
   in the selected frames. It runs the modules on one `cudaStream_t` and synchronizes only where the
   CPU needs data (Kabsch and the sizes N, M, K).
2. **Tests.** Each test in `tests/` runs one module on the reference input and compares its output
   with the reference, with tolerances:
   - ~1e-4 relative on tensors, in FP32;
   - ≥ 99 % identical labels;
   - poses within 1 cm.
   Add them to CMake with `enable_testing()` / `add_test()` and run them with `ctest`.
3. **Program output.**
   - a `.bin` with the static/moving label and object ID for every point, plus the poses;
   - optionally, a `.ply` colored by object, to open in CloudCompare or MeshLab (useful for the demo).

### Phase 7 - Optimization

1. **FP16.** Enable `BuilderFlag::kFP16` when building engines. If accuracy drops, keep the sensitive
   layers (L2 normalization, the `ego_ot` affinity) in FP32 with per-layer precision constraints.
2. **INT8.** Calibrate in C++ with `IInt8EntropyCalibrator2` (still works in TensorRT 10.3, but
   deprecated). Calibrate only `backbone` and `stpn`, where most of the compute is, with inputs from
   the selected frames. Compare accuracy with FP16.
3. **CUDA Graphs.** The fixed-shape part (backbone + surrounding kernels) can be captured in a graph
   (`cudaStreamBeginCapture`) to reduce launch overhead. This matters on the Jetson.
4. **Streaming.** Keep `bev_feats` for the last 4 frames in a ring buffer. For a new frame, run the
   backbone only on that frame, with a second `backbone` engine of batch 1. The rest of the pipeline
   is recomputed normally.
5. **Jetson shared memory.** For input/output use pinned memory (`cudaHostAlloc`) or
   `cudaMallocManaged`, to avoid needless CPU↔GPU copies.

### Phase 8 - Measurements on the Jetson

1. **Setup:** `sudo nvpmodel -m <mode>` and `sudo jetson_clocks`. Run `tegrastats` alongside the
   benchmark for power (W), RAM and temperature.
2. **`benchmark.cpp`** runs the pipeline on the selected frames and writes a CSV with:
   - per-module latency, measured with `cudaEvent`;
   - FPS;
   - peak memory.
3. **Profiling:** `nsys profile ./pcacc ...` shows the full timeline: where the GPU waits, how long
   each kernel takes.

Compare the variants on per-module latency, end-to-end FPS, peak memory, average power, energy per

## 7. Risks and mitigations

- **Workload.** The longest part is porting the non-dense logic: preprocessing, ego-motion,
  clustering. TubeNet stays optional. If behind schedule, DBSCAN can temporarily run on the CPU in
  C++ (2D grid + BFS), with the CUDA version later.
- **ONNX export fails.** Export only the wrappers with dense ops. Do not export the whole `MotionNet`.
  Everything data-dependent (masks, `torch_scatter`, `randperm`, `.item()`) stays outside the graph
  and is done in CUDA.
- **Numerical differences between C++ and Python.** Test each module separately, on the exact
  reference input, not only the full pipeline. Otherwise you can't tell where a difference appears.
- **Installing TensorRT on the laptop.** The 10.3 C++ version must be compatible with the laptop's
  CUDA 12.x. If that's a problem, use the matching NVIDIA TensorRT container.
- **Memory on the Jetson.** Building engines uses a lot of memory. Limit the workspace
  (`setMemoryPoolLimit`), run without the GUI and add temporary swap if needed.

## Running the Python reference (details in `RUNNING.md`)

- `python dummy-test.py`: loads `checkpoints/waymo.pth` onto the GPU and builds a torchsparse tensor.
- `python benchmarks/bench_v0.py`: speed benchmark of the original model on the selected real
  frames, batch 1, `test` mode. Times each stage of the module table (`preprocess`, `voxelize`,
  `h2d`, `pillar_enc`, `backbone`, `ego_motion`, `motion_seg`, `cluster`, plus `tubenet` outside
  the scope) through the optional `MotionNet.timer` hook (no-op when `None`). Writes
  `benchmarks/results/<variant>_<device>.csv` with columns
  `variant,device,precision,frame,pass,stage,ms,n_points,n_pillars,n_fg_points`. **The C++
  `benchmark.cpp` must write the same schema and stage names**, so `benchmarks/summarize.py`
  (numpy only) compares any runs: median ms per stage, e2e, FPS, speedup vs V0.
- `e2e` = sum of synced stages `preprocess`..`cluster`; `e2e_nosync` = a second run without
  per-stage syncs. Benchmark focus is speed; power and memory are not measured.
- Regression workflow: `--deterministic --passes 1 --save-outputs benchmarks/results/V0_outputs`
  once on the original model, then `--deterministic --passes 1 --compare <dir>` after each change.
  Per-frame `.bin` files (format in `benchmarks/binio.py`: int32 dtype code, ndim, dims, data):
  `points`, `poses [5,4,4]`, `mos_label [N]`, `inst_label [N]`.
- Always use `--deterministic` for comparisons. Without it, fp32 runs differ slightly from run to
  run, and occasionally a point changes instance cluster.
- In `train`/`val` mode the forward pass uses ground-truth labels. Always run in **`test` mode**,
  which is the deployment path.

## V0 baseline (RTX 4060 Laptop, TF32 convs, batch 1, 273 real frames × 3 passes, 2026-11-15)

- Inputs after preprocessing (median, min–max): 357k points (26k–608k), 17.9k 4D pillars
  (3.2k–43k), 81k foreground points sent to STPN (0–348k). Latency scales with these.
- Median ms per stage: preprocess 6.5, voxelize 8.1, h2d 2.0, pillar_enc 21.5, backbone 36.1,
  ego_motion 7.4, motion_seg 31.6, cluster 25.9 (tubenet 14.8, outside the scope).
- **e2e median 143.9 ms, p90 189.7 ms, 6.75 FPS** (min 63 ms, max 375 ms). No-sync e2e is the
  same (143.5 ms), so per-stage syncs cost almost nothing.
- Ego-motion translation error vs GT: ~0.03 m. If it's suddenly much larger, something broke.
- `--deterministic` noise floor: identical labels, pose diff ~0.002 cm.
- Results: `benchmarks/results/V0_NVIDIA-GeForce-RTX-4060-Laptop-GPU-sm-89.csv` (git-ignored).

## Known issues / porting notes

- **fp16 autocast fails** at `models/motionnet.py:224` (`full_mos[fb_mask] = mos`, a
  float32/float16 mismatch). Irrelevant for TensorRT FP16 (engine I/O can stay FP32), but expect
  more spots like it if mixed precision is tried in PyTorch.
- Voxelisation (`libs/voxel_generator.py`) is a numba loop on the **CPU**; it would be slow on the
  Jetson's ARM cores, hence `voxelize.cu`.
- The ego-motion head builds four 1024×1024 `perm_matrix` tensors per scene and samples points
  with `torch.randperm` (non-deterministic across implementations).
- Instance clustering + TubeNet is data-dependent and hard to export to TensorRT (hence clustering
  in CUDA, TubeNet optional).
